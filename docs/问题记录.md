# 问题记录

## 预览编辑 Markdown 回写

### 背景

YKMarkdown 的预览区域是可编辑的 WebKit 页面。早期实现中，用户在预览中输入后，页面会把整个 `content.innerHTML` 通过 Turndown 转回 Markdown，再整体写回原文。

这个策略对简单段落可用，但它不是无损操作。Markdown 源码里有很多语法细节在渲染为 HTML 后会丢失，例如列表缩进风格、标题文字里的转义策略、表格原始排版、空行数量和局部写法偏好。

### 触发过的问题

在一篇包含标题、列表和表格的文档中，用户只修改了首段一句话：

```markdown
本文档说明 YKImageEditor 当前各项图片编辑功能的实现方式、数据流、性能策略和扩展边界。内容对应当前工程代码，不是产品规划文档。
```

保存后 Git 却显示大量 diff。实际原因不是文件编码或行尾变化，而是预览编辑把整篇文档重新序列化：

- `## 1. 技术架构` 被转成 `## 1\. 技术架构`。
- `- xxx` 被转成 `-   xxx`。
- Markdown 表格被拆成普通段落文本。
- 未编辑区域也被写成 Turndown 的默认 Markdown 风格。

其中表格问题尤其严重，因为基础 Turndown 没有 GFM table 规则，HTML 的 `<table>` 回写时会退化为单元格文本。

后续又复现过一次更具体的场景：用户在预览区的 Markdown 表格单元格中编辑内容后，全文出现格式漂移：

- 有序列表从 `1. 内容` 被改成 `1.  内容`，编号后多出一个空格。
- 无序列表也可能从 `- 内容` 被改成 `-   内容`。
- 表格分隔行从紧凑写法或带对齐标记的写法，例如 `|---:|---|---|`，被改成 `| --- | --- | --- |`。
- 用户实际只改了表格中的局部文字，但 Git diff 看起来像全文列表和表格都被重排。

这次的根因不是表格渲染本身，而是预览区编辑事件里当前 selection 有时无法稳定向上找到带 `data-source-offset` 的顶层表格块。一旦定位失败，前端会退回 `currentMarkdown()` 全量回写，整篇文档都会经过 Turndown 默认规则重新序列化，于是列表 marker 空格和表格分隔行被改成 Turndown 的默认风格。

### 曾经的块级处理

预览编辑曾经先改成优先走块级回写：

1. 渲染器继续为顶层 Markdown 块写入 `data-source-offset`。
2. 预览发生输入时，JavaScript 侧定位当前光标所在的顶层块。
3. 页面只把这个块转成 Markdown，并通过 `markdownBlockChanged` 上报块起始 offset 和块内容。
4. Swift 侧使用原文的 source offsets 定位块范围，只替换这个块，保留其他未编辑 Markdown 原文。
5. 只有无法定位块，或一次操作可能跨多个块时，才退回全量回写。

这个版本仍然不够安全，因为剪切、普通粘贴、插图和跨块编辑都会主动设置全文回写；表格内编辑时如果 selection 仍然定位失败，也会再次触发整篇 Turndown。

### 当前处理

预览编辑现在不再保留 `markdownChanged` 全文回写入口，统一走范围回写：

1. `beforeinput` 优先从 `getTargetRanges()` 读取本次编辑影响的 DOM 范围。
2. JS 将范围两端映射到带 `data-source-offset` 的顶层 Markdown 块，得到 `startSourceOffset` 和 `endSourceOffset`。
3. 输入完成后，只把这个 offset 范围内当前 DOM 块转成 Markdown，并通过 `markdownRangeChanged` 上报。
4. Swift 侧用原文 source offsets 将这个范围替换回 Markdown 原文，其它范围不经过 Turndown。
5. 如果前端无法定位受影响范围，就不静默回写，避免用全量序列化污染整篇文档。

剪切、普通粘贴、跨块编辑和预览插图都应进入同一套范围 patch。空文档会渲染一个带 `data-source-offset="0"` 的占位段落，Swift 侧允许 offset 0 从空文档生成第一段内容。

同时预览侧为标题和表格补了专用 Turndown 规则，降低单块回写时的格式噪音：

- 标题内容中普通的 `1. ` 不再被转义成 `1\. `。
- `<table>` 会按 GFM 表格格式回写，而不是拆散成普通文本。
- 列表项回写使用 `1. ` / `- ` 这种单空格 marker，避免受影响列表块被额外插入空格。
- 表格 DOM 会记录原始分隔行，范围回写时优先保留 `|---:|---|---|` 等原有对齐和紧凑写法。

Swift 侧也增加了表格分隔行兜底保护：即使前端传回的单块 Markdown 已经被规范化为 `| --- | --- |`，只要原块和替换块列数一致，就保留原文第二行的表格分隔写法。

### 实现对照

下面三段代码不是同一个时期的实现。它们按时间顺序记录回写策略的演进，只有“当前实现”代表现在仓库里的代码。

#### 最早旧实现：全文回写

这个版本已经不在当前代码中。它只有一个全量回写入口。预览区任意输入都会把整个 DOM 转成 Markdown，再整体替换文档内容：

```javascript
function currentMarkdown() {
  return turndown.turndown(content.innerHTML || '');
}

function emitMarkdown() {
  if (suppressEmit) return;
  post({ type: 'markdownChanged', markdown: currentMarkdown() });
}
```

Swift 侧收到后直接把整篇 Markdown 写回：

```swift
case "markdownChanged":
    guard let markdown = body["markdown"] as? String else { return }
    let normalized = Self.normalizeMarkdown(markdown)
    parent.onMarkdownChange(normalized)
```

#### 中间旧实现：块级优先，但仍有全文 fallback

这个版本也已经不在当前代码中。它优先定位当前编辑的顶层块，只上报块起点和块内容；但如果定位失败或判断为跨块编辑，仍会走 `markdownChanged` 全文回写：

```javascript
function emitMarkdown() {
  if (suppressEmit) return;
  if (pendingPreviewEdit.requiresFullEmit || !pendingPreviewEdit.block) {
    post({ type: 'markdownChanged', markdown: currentMarkdown() });
  } else {
    post({
      type: 'markdownBlockChanged',
      sourceOffset: pendingPreviewEdit.block.sourceOffset,
      markdown: pendingPreviewEdit.block.markdown
    });
  }
}
```

对应的 Swift 侧只替换原文中对应 `sourceOffset` 的块范围，未编辑区域不会经过 Turndown：

```swift
case "markdownBlockChanged":
    let patched = MarkdownPreviewEditPatch.replacingBlock(
        in: lastAppliedMarkdown,
        sourceOffset: sourceOffset.intValue,
        with: markdown
    )
    parent.onMarkdownChange(Self.normalizeMarkdown(patched))
```

#### 当前实现：范围回写，无全文 fallback

这是现在仓库里的代码。当前实现移除了 `markdownChanged` 全文分支，只发送 `markdownRangeChanged`；如果无法确认受影响范围，就不回写，避免整篇 Markdown 被 Turndown 重排：

```javascript
function emitMarkdown() {
  if (suppressEmit) return;
  const range = pendingPreviewEdit.range;
  pendingPreviewEdit.range = null;
  if (!range) return;
  post({
    type: 'markdownRangeChanged',
    startSourceOffset: range.startSourceOffset,
    endSourceOffset: range.endSourceOffset,
    markdown: markdownForRange(range)
  });
}
```

### 后续注意

可编辑预览无法天然做到 Markdown 源码级无损编辑。只要经过 `HTML -> Markdown`，被编辑的块仍可能丢失局部写法，例如表格列对齐空格、复杂内联 HTML 或非标准 Markdown 扩展。

如果以后继续增强预览编辑，优先考虑这些方向：

- 对常见块类型做局部 patch，不要恢复全量回写作为默认路径。
- 对表格、代码块、引用、列表等结构块分别补回写规则。
- 对跨块粘贴、删除、拖拽插入等操作单独设计 range patch，避免用整篇 Turndown 兜底。
- 修改回写策略时，用包含标题编号、列表、表格和代码块的文档检查 Git diff。

## 预览区右键菜单注入

### 背景

YKMarkdown 的文档区域分为源码编辑区和预览编辑区：

- 源码编辑区基于 `NSTextView`。
- 预览编辑区基于 `WKWebView`，页面内容通过 `contenteditable` 实现可编辑预览。

为了让用户能从右键菜单快速定位当前 Markdown 文件，曾尝试在源码区和预览区的系统右键菜单末尾追加 `Show in Finder`。

### 触发过的问题

源码编辑区右键菜单已经出现 `Show in Finder`，但预览区右键菜单没有出现。

初始实现只覆盖了 `PreviewWKWebView.menu(for:)`，期望在 `WKWebView` 返回系统菜单时追加自定义菜单项。实际运行时，预览区右键菜单仍然只显示 WebKit/系统提供的文本菜单，例如 Look Up、Translate、Cut、Copy、Paste、Spelling and Grammar、Services 等。

### 原因

macOS 上 `WKWebView` 的可编辑内容菜单不一定由外层 `WKWebView` 本身直接生成。右键发生在 WebKit 内部子视图或内部编辑视图上时，系统菜单可能绕过外层 `PreviewWKWebView.menu(for:)`。

同时，当前 SDK 中 `WKUIDelegate` 的现代 context menu 定制接口主要暴露给 iOS/visionOS，macOS 的 `WKWebView` 没有等价的公开 delegate 回调可以直接修改这类系统菜单。

因此，单纯覆盖外层 `WKWebView.menu(for:)` 只能覆盖一部分路径，无法保证预览区 `contenteditable` 菜单一定带上自定义项。

### 当前处理

源码编辑区继续使用 `MarkdownTextView` 子类，在 `menu(for:)` 中基于 `NSTextView` 的系统菜单追加 `Show in Finder`。

预览区额外增加了一个 AppKit 层的兜底路径：

1. `PreviewWKWebView` 安装本地鼠标事件监听。
2. 当右键或 Control-click 发生在当前 `WKWebView` 范围内，且当前文档是本地 file URL 时，短时间标记一次即将出现的上下文菜单。
3. 监听 `NSMenu.didBeginTrackingNotification`。
4. 如果菜单开始跟踪时仍处于这次预览区右键事件窗口内，就把 `Show in Finder` 追加到该菜单。
5. 点击菜单项后调用 `NSWorkspace.shared.activateFileViewerSelecting([documentURL])`，在 Finder 中选中当前文档。

这个方案保留 WebKit 原生菜单内容，只在末尾追加自定义入口。未保存文档没有本地文件 URL，因此不会显示该菜单项。

### 后续注意

这类处理依赖 AppKit 菜单开始跟踪通知，而不是 WebKit 的专门公开扩展点。它比私有 API 稳定，但仍然要注意作用域，避免把菜单项追加到其它区域的菜单里。

后续如果继续扩展预览区右键菜单，应保持这些约束：

- 只在确认右键事件来自当前 `PreviewWKWebView` 时注入。
- 只对本地已保存文档显示 Finder 相关操作。
- 保留系统菜单，不重建 WebKit 的默认 Cut/Copy/Paste、拼写、服务等菜单项。
- 如果需要多个自定义项，优先复用统一 helper，避免重复追加或污染其它菜单。

## Swift 6 菜单监听隔离问题

### 背景

为了解决预览区右键菜单没有出现 `Show in Finder` 的问题，曾给 `PreviewWKWebView` 增加 `NotificationCenter.default.addObserver(forName:object:queue:using:)` block observer，在 `NSMenu.didBeginTrackingNotification` 触发时向菜单追加自定义项。

### 触发过的问题

项目使用 Swift 6 并发检查时，`MarkdownPreviewView.swift` 编译失败，核心报错包括：

- `result of call to 'appendingShowInFinderItem(to:documentURL:target:action:)' is unused`
- `main actor-isolated property 'contextMenuEventExpiresAt' can not be referenced from a Sendable closure`
- `main actor-isolated property 'contextMenuEventExpiresAt' can not be mutated from a Sendable closure`
- `main actor-isolated property 'documentURL' can not be referenced from a Sendable closure`

### 原因

`WKWebView` 属于 AppKit/WebKit UI 类型，相关实例状态在 Swift 6 下会被视为主 actor 隔离。`NotificationCenter` 的 block observer 使用的 closure 需要满足 Sendable 约束，不能直接读取或修改 `PreviewWKWebView` 的主 actor 隔离属性。

另外，`DocumentContextMenu.appendingShowInFinderItem(...)` 返回 `NSMenu?`。在严格警告作为错误处理时，直接调用但不使用结果也会导致编译失败。

### 原写法

```swift
private var menuTrackingObserver: NSObjectProtocol?

private func installContextMenuObservers() {
    menuTrackingObserver = NotificationCenter.default.addObserver(
        forName: NSMenu.didBeginTrackingNotification,
        object: nil,
        queue: .main
    ) { [weak self] notification in
        guard let self,
              let menu = notification.object as? NSMenu,
              let menuEventExpiresAt = self.contextMenuEventExpiresAt,
              Date() <= menuEventExpiresAt
        else {
            return
        }

        self.contextMenuEventExpiresAt = nil
        DocumentContextMenu.appendingShowInFinderItem(
            to: menu,
            documentURL: self.documentURL,
            target: self,
            action: #selector(showDocumentInFinder)
        )
    }
}
```

### 修正写法

改为 selector observer，让通知回调进入 `@objc` 实例方法，避免 Sendable closure 直接访问主 actor 隔离状态；同时显式丢弃菜单 helper 的返回值。

```swift
nonisolated(unsafe) private var contextMenuEventMonitor: Any?

private func installContextMenuObservers() {
    NotificationCenter.default.addObserver(
        self,
        selector: #selector(menuDidBeginTracking),
        name: NSMenu.didBeginTrackingNotification,
        object: nil
    )
}

@objc private func menuDidBeginTracking(_ notification: Notification) {
    guard let menu = notification.object as? NSMenu,
          let menuEventExpiresAt = self.contextMenuEventExpiresAt,
          Date() <= menuEventExpiresAt
    else {
        return
    }

    self.contextMenuEventExpiresAt = nil
    _ = DocumentContextMenu.appendingShowInFinderItem(
        to: menu,
        documentURL: self.documentURL,
        target: self,
        action: #selector(showDocumentInFinder)
    )
}
```

`contextMenuEventMonitor` 使用 `nonisolated(unsafe)` 是因为 `deinit` 在 Swift 6 严格并发下是 nonisolated，而 `NSEvent.addLocalMonitorForEvents` 返回的 token 类型是 `Any?`、不满足 Sendable。该 token 只用于同一 UI 对象生命周期内注册和移除本地事件监听。

### 后续注意

以后给 AppKit/WebKit UI 类型增加通知、异步回调或事件监听时，需要先判断回调 closure 是否是 Sendable。若 closure 需要访问 UI 对象状态，优先考虑 selector、delegate、主 actor 方法，或明确把状态复制为 Sendable 值后再进入 closure。

如果必须保存 AppKit 返回的非 Sendable 监听 token，并且只在 UI 对象生命周期内使用，需要显式隔离设计；不要让非 Sendable token 进入跨线程数据流。

## 解决冲突时窗口弱引用崩溃

### 背景

文档手动刷新进入三方合并后，`EditorView` 会从普通编辑/预览布局切换到 `DocumentMergeConflictView`。这个视图切换仍然保留 `DocumentWindowConfigurator` 和 `DocumentSearchWindowReader` 这类 SwiftUI/AppKit 桥接视图，用来读取当前 `NSWindow` 并配置文档标签页、全局搜索跳转。

`DocumentWindowConfigurator.Coordinator` 早期用 `weak var window: NSWindow?` 记录上一次配置过的窗口，目的是在同一个窗口上避免重复尝试加入标签页。

### 触发过的问题

用户解决冲突时 App 崩溃，崩溃报告显示主线程触发 `EXC_CRASH (SIGABRT)`，核心栈落在：

```text
weak_register_no_lock
objc_storeWeak
swift_unknownObjectWeakAssign
DocumentWindowConfigurator.configure(window:coordinator:)
DocumentWindowConfigurator.updateNSView(_:context:)
```

崩溃时 AppKit 同时在执行窗口和视图 detach/dealloc 相关路径，例如 `-[NSWindow dealloc]`、`-[NSView _setWindow:]`。这说明问题发生在窗口生命周期切换期间，而不是三方合并算法本身。

### 原因

`NSViewRepresentable.updateNSView` 和 `viewDidMoveToWindow()` 可能在 SwiftUI 切换冲突界面、窗口关闭、标签页拆装或视图脱离窗口时被调用。此时 `view.window` 返回的 `NSWindow` 可能正处在销毁流程中。

如果这时把该窗口写入 `weak var window`，Swift 会调用 Objective-C runtime 注册 weak 引用。对正在 dealloc 的 Objective-C 对象注册 weak 引用是不安全的，runtime 会直接 abort，因此崩溃点表现为 `objc_storeWeak` / `weak_register_no_lock`。

同类风险也存在于其它“只是为了记住上一次窗口”的桥接代码中：如果并不需要持有窗口对象本身，就不应把 `NSWindow` 存进 weak 属性里。

### 当前处理

`DocumentWindowConfigurator.Coordinator` 不再保存 weak `NSWindow`，改为保存 `ObjectIdentifier`：

```swift
private(set) var configuredWindowID: ObjectIdentifier?
var configuredMode: DocumentOpeningMode?

func updateWindowIdentity(_ id: ObjectIdentifier) -> Bool {
    guard configuredWindowID != id else { return false }
    configuredWindowID = id
    configuredMode = nil
    didAttemptInitialTabbing = false
    return true
}
```

配置窗口时只在窗口身份变化，或文档打开模式变化时，才重新写入 `tabbingIdentifier` 和 `tabbingMode`。这样可以保留原来的标签页行为，同时避免在窗口销毁期间向 weak 存储写入 `NSWindow`。

`DocumentSearchWindowReader.WindowReaderView` 也同步改为用 `ObjectIdentifier` 记录已观察和已上报的窗口。关闭通知移除时不再依赖保存的 weak window，而是通过当前 observer 统一移除对应通知注册。

### 后续注意

SwiftUI/AppKit 桥接视图里，`view.window` 适合在当前调用栈内立即使用，不适合为了“比较是不是同一个窗口”而保存为 weak 属性。后续遇到类似需求，优先保存 `ObjectIdentifier(window)`、窗口编号或其它稳定身份值。

只有在确实需要后续操作窗口对象时，才保存 weak `NSWindow`；并且要特别避开 `viewDidMoveToWindow()`、`updateNSView`、窗口关闭通知、标签页重组等窗口生命周期正在变化的时机。

如果只是为了防止重复配置、重复上报或重复注册监听，不要保存对象引用，保存身份值通常更安全。

## Markdown 解析兼容性不完整

持续更新的功能待办与完成状态见 [Markdown 解析补全清单](Markdown%20解析补全清单.md)。本节保留问题背景与 2026-09-06 的支持情况快照。

### 背景

截至 2026-09-06，预览使用 `Sources/Infrastructure/Rendering/MarkdownHTMLRenderer.swift` 中自行实现的简化解析器，通过逐行判断和正则替换生成 HTML，尚未完整实现 CommonMark 或 GFM。预览编辑后的 HTML 使用 Turndown 回写 Markdown；回写能力与正向解析能力需要分别检查。

Markdown 没有所有软件统一遵循的“最新版”，主要有这些规范与方言：

| 规范 | 定位 |
| --- | --- |
| 原始 Markdown | 最初的语法说明，部分边界情况没有严格定义 |
| CommonMark | 将解析规则、优先级和边界情况明确下来，便于不同实现保持一致 |
| GFM | GitHub 使用的方言，在 CommonMark 上增加表格、任务列表、删除线等扩展 |

参考：[原始 Markdown 语法](https://daringfireball.net/projects/markdown/syntax)、[CommonMark 规范](https://spec.commonmark.org/0.31.2/)、[GFM 规范](https://github.github.com/gfm/)。

### 触发过的问题

1. 源码中的父子列表在预览中显示为同一级。解析前删除了行首缩进，随后所有条目被放进同一个列表，丢失父子结构。
2. 单独一行的 `* * *` 显示为一个蓝色圆点。旧实现只识别 `---` 分隔线，开头的 `* ` 被当作列表标记，剩余的 `* *` 被当作内容为空格的斜体。

`***`、`* * *`、`---`、`___` 本身都是合法分隔线写法。这类问题属于当前解析器的实现缺失，不能解释为用户使用了不同版本的 Markdown。

### 当前处理

- 已补充按缩进维护的列表层级栈，支持常见父子列表、多级回退、有序与无序列表混用，以及空格和 Tab 缩进。源码锚点仍保留在最外层列表，以兼容整块编辑回写。
- 已在列表解析前统一识别分隔线：至少三个同类星号、横线或下划线，标记之间允许空格和 Tab，行首最多三个空格。连续多条分隔线各自保留 HTML 节点和源码锚点。
- 已在 `Tests/AppTests.swift` 补充列表与分隔线回归用例。源码差异检查通过；未编译或运行测试，不能视为已通过标准一致性测试。

### 尚未支持或仅部分支持的语法

以下为当前源码静态核对结果，包含基础语法及扩展语法，并非完整的一致性测试报告。

| 功能 | 当前缺口 |
| --- | --- |
| 标题 | 未支持 Setext 标题（文字下方的 `===`、`---`）；未正确处理 `## 标题 ##` 的尾部标记 |
| 有序列表 | 未支持 `1)` 标记，也未保留非 1 的起始编号 |
| 复杂列表 | 条目内的多段文字、代码块、引用、标题，以及完整的缩进与松紧列表规则尚未支持 |
| 引用 | 仅处理简单引用；嵌套引用及引用内的块级内容未完整支持 |
| 代码块与行内代码 | 未支持波浪号围栏、缩进代码块和多反引号代码跨度；围栏长度匹配不完整 |
| 加粗与斜体 | 常见写法可用，复杂嵌套和标记边界规则不完整，普通下划线可能误触发格式 |
| 转义与换行 | 未正确实现反斜杠转义，以及行尾两个空格或反斜杠产生的强制换行 |
| 链接与图片 | 简单写法可用；引用式链接、标题属性、地址中的嵌套括号不完整或未支持 |
| 自动链接 | 未支持尖括号包围的网址和裸网址自动识别 |
| HTML 与实体 | 原始 HTML 按文字显示，字符实体未按标准解码 |
| 表格 | 基础表格可用；列对齐未生效，单元格内转义的竖线会被错误拆列 |
| 任务列表 | `- [ ]`、`- [x]` 未显示为复选框 |
| 其他扩展 | 脚注、数学公式未支持；Mermaid 和简单删除线已有支持 |

### 后续注意

列表层级和分隔线的局部修复不等于完成 CommonMark/GFM 支持。特别是文字下一行的 `---` 与 Setext 标题之间的优先级，本次分隔线修复未处理。

如果后续目标是稳定预览常见 Markdown 文档，应先明确采用的规范与扩展范围，再评估成熟的 CommonMark/GFM 解析器。接入时需要同时设计源码位置映射、预览编辑回写和 Mermaid 的兼容方式，避免仅替换 HTML 输出后破坏已有编辑流程。

# Markdown 文件外部变更监听方案

## 目标

YKMarkdown 当前只在打开文档时读取一次磁盘内容。若同一个 `.md` 被其他编辑器或脚本修改，已打开窗口里的 `document.text` 不会自动更新。目标是为已保存或已打开的 Markdown 文档增加外部变更感知能力，让应用能在安全的前提下同步磁盘新内容。

这项能力不应静默覆盖用户在 YKMarkdown 内部尚未保存的修改。实时监听只负责发现磁盘变化，最终是否自动载入要由内容比对和冲突策略决定。

## 机制比较

### NSFilePresenter

`NSFilePresenter` 是 Apple 文件协调体系的一部分，适合 document-based app 与 `NSFileCoordinator`、iCloud、沙盒文件访问等机制配合使用。它的语义清晰，可以表达 presented item 变更、移动、删除等事件。

它的问题是依赖文件协调生态。外部编辑器、命令行工具或同步脚本可能只是直接写文件，或者用临时文件替换原文件，并不一定完整触发协调通知。单独依赖 `NSFilePresenter` 可能无法覆盖所有普通本地编辑场景。

### DispatchSource

`DispatchSourceFileSystemObject` 可以基于文件描述符监听 `.write`、`.rename`、`.delete`、`.extend`、`.attrib` 等事件。它实现轻，适合当前项目这种只关心已打开文档外部变化的场景。

不能只监听目标文件本身。很多编辑器保存文件时会采用原子保存：先写临时文件，再 rename 替换原文件。此时旧文件描述符可能已经不再代表新的路径，监听目标文件本身容易漏事件或失效。更稳妥的做法是监听目标文件所在的父目录，然后在事件到达后重新检查目标 `fileURL`。

### FSEvent

FSEvent 面向目录树级别的文件系统事件流，适合监听整个 workspace、文件树或大量文件。它覆盖范围大，但事件粒度更粗，API 更底层，业务侧仍需要自行过滤目标路径和去抖。

对于每个文档只关心自己所在目录里的一个 `.md` 文件，直接引入 FSEvent 偏重。除非后续要做整个文件夹工作区、文件树同步或批量文档监控，否则不作为第一选择。

## 推荐方案

第一阶段采用 **DispatchSource 监听父目录 + 目标文件内容比对**。

每个打开的已保存文档都创建一个轻量监听对象，监听 `fileURL.deletingLastPathComponent()`。收到目录写入、重命名、删除等事件后，不直接相信事件内容，而是延迟一小段时间重新读取当前 `fileURL` 的文件属性和内容。

选择这个方案的原因：

- 能覆盖常见编辑器的原子保存，因为监听对象绑定的是父目录而不是旧文件本身。
- 实现量小，适合先解决单文档实时同步问题。
- 不引入全局文件树监听，避免对当前项目过度设计。
- 与现有手动刷新逻辑一致，最终仍通过同一套内容比对和冲突处理路径更新 `document.text`。

`NSFilePresenter` 可以作为后续增强，特别是当应用需要更严肃地接入 document-based file coordination、iCloud 或文件移动通知时。FSEvent 留给未来 workspace 级监听。

## 监听与比对流程

新增 `DocumentFileChangeMonitor`，职责只包含监听磁盘变化并回调，不直接修改文档内容。

核心流程：

1. `EditorView` 在 `fileURL != nil` 时创建或更新 monitor。
2. monitor 打开父目录文件描述符。
3. monitor 使用 `DispatchSourceFileSystemObject` 监听父目录的 `.write`、`.rename`、`.delete`、`.extend`、`.attrib`。
4. 收到事件后做 200-500ms debounce，避免一次保存触发多次读取。
5. debounce 后回到主线程通知 `EditorView` 检查目标文件。
6. `EditorView` 读取当前 `fileURL` 内容，和内存状态比较。
7. 根据冲突策略决定忽略、自动载入或提示用户。

monitor 生命周期跟随每个 `EditorView`，因此多文档打开时，每个窗口或标签只监听自己的文档所在目录，不会刷新其他文档。

## 状态模型

`EditorView` 需要维护三个版本概念：

- `base`：上次确认和磁盘一致的内容，也就是 `lastKnownDiskText`。
- `local`：当前 YKMarkdown 内存里的 `document.text`。
- `remote`：监听到变化后，从磁盘重新读取到的内容。

基础判断：

- `remote == local`：磁盘和当前内容一致，忽略，并更新 `base`。
- `local == base` 且 `remote != base`：只有外部修改，自动载入 `remote`。
- `local != base` 且 `remote == base`：只有本地修改，不处理。
- `local != base` 且 `remote != base`：本地和外部都修改过，进入冲突处理。

第一阶段的“冲突”是文档级冲突，不判断是否修改了同一行或同一段。只要本地和外部都偏离 `base`，就不自动覆盖。

## 冲突处理

第一阶段不做 Git 风格三方 merge。原因是自动合并需要稳定的 diff/merge 算法和额外 UI，否则容易在 Markdown 表格、列表、段落重排时生成不可靠结果。

文档级冲突时，界面应提供轻量提示，而不是立即弹阻塞式 alert。提示内容表达为：

`磁盘上的文件已更新，且当前文档有未保存修改。`

可选操作：

- `载入磁盘版本`：用 `remote` 替换 `document.text`。
- `保留当前版本`：忽略本次 `remote`，继续保留 `local`。
- `另存当前版本...`：将 `local` 保存成副本，再允许用户载入 `remote`。

如果实现成本需要继续收敛，第一版至少要在执行 `载入磁盘版本` 前自动写一份冲突备份，避免用户的 App 内部修改不可恢复。备份文件名建议为：

`<filename>.ykmarkdown-conflict-<yyyyMMdd-HHmmss>.md`

手动刷新按钮保留，并复用同一套冲突判断。区别只是触发来源不同：一个来自用户点击，一个来自磁盘事件。

## 后续三方合并方向

如果要做成类似 Git 的冲突解决，需要在 `base`、`local`、`remote` 三个版本之间做三方 merge。

建议分阶段：

1. 行级三方 merge：自动合并不重叠的行区间修改。
2. 重叠修改插入冲突标记：

   ```markdown
   <<<<<<< YKMarkdown
   本地内容
   =======
   外部磁盘内容
   >>>>>>> Disk
   ```

3. 再做可视化冲突解决 UI，提供 `使用本地`、`使用外部`、`两者都保留`、`手动编辑`。

三方 merge 不应作为实时监听第一阶段的前置条件。先实现可靠的发现、比对、提示和安全载入，再逐步增强合并体验。

## 实现步骤

1. 新增 `DocumentFileChangeMonitor`。
   - 输入：`fileURL`、变化回调。
   - 内部监听父目录，不监听目标文件本身。
   - 支持取消监听，避免文档关闭后继续持有文件描述符。

2. 在 `EditorView` 接入 monitor。
   - `fileURL` 为空时不监听。
   - `fileURL` 变化时重建 monitor。
   - `onDisappear` 时取消监听。

3. 抽取磁盘重载判断。
   - 将手动刷新和监听刷新统一走同一个方法。
   - 读取失败时展示现有错误提示。
   - `remote == local` 时静默忽略。
   - 无本地冲突时自动应用 `remote`。

4. 增加外部变更冲突提示状态。
   - 保存 `pendingRemoteText`。
   - 保存冲突来源文件名。
   - 提供载入磁盘版本和保留当前版本操作。

5. 增加冲突备份保护。
   - 在覆盖 `local` 前写入同目录备份。
   - 备份失败时不继续覆盖，提示用户。

6. 补充验证。
   - 手动刷新：无变化、仅外部变化、本地和外部同时变化。
   - 外部编辑器直接保存。
   - 外部编辑器原子保存。
   - 文件被删除或临时不可读。
   - 多文档同时打开，只刷新发生变化的当前文档。

## 风险和边界

父目录监听会收到同目录其他文件变化，因此必须在回调后重新检查目标 `fileURL`，不能仅凭事件刷新文档。

保存过程可能产生多次事件，需要 debounce，否则会重复读取、重复提示。

文件可能在事件触发时仍处于写入中，读取失败或读到半成品时不应立刻覆盖当前内容。可以短延迟重试一次，仍失败再提示。

第一阶段不解决行级合并问题。只要本地和外部都修改过，就按文档级冲突处理。
